# AI 图片编辑实施方案

> 状态：用户已授权实施；编辑基础链路和既有图片入口已接入代码，隔离测试与构建通过；真实模型及人工验收未完成，详见第 12 节。
> 需求依据：[AI 图片编辑 PRD](./ai-image-edit-prd.md)。本文细化技术实现，不替换 PRD。
> 调查基线：`main`，提交 `b658da9`。实施不包含提交、推送、修改版本号、打 tag 或发布。
> 下文保留设计合同与验收判据，不把代码接入等同于完整验收。外部模型后端尚未实现，生产编辑调用保持明确不可用，真实调用及端到端验收仍待接口就绪。

## 1. 调查结论与最小方案

采用 **一个共用编辑窗口 + 独立的临时编辑会话 + 原业务保存逻辑**：

1. 各页面把实际选中的图片、目标对象/槽位和原引用快照传给同一个编辑窗口。
2. 编辑请求使用新的 `image_edit` 服务，不复用普通生图的业务入口，不自动回退文生图。
3. 原图副本、遮罩、每轮结果先放会话临时目录；生成阶段不写业务图片历史，不改任何业务引用。
4. 用户采用后，最终文件才进入既有工程/公共目录；沿用目标原来的字段、图片记录和首尾帧绑定语义。
5. 保存及引用更新成功后才关闭窗口、清理临时数据；失败保留结果供重试。

不加绘图依赖、工作流引擎、全局素材抽象或多轮历史库。前端用现有 Vue/Element Plus 与原生 Canvas、Pointer Events；后端用现有 SQLite、任务服务、`sharp` 和文件存储。

**不能直接复用的“近似能力”：**

- `imageService.create/processImageGeneration` 会创建 `image_generations`，并在完成时更新资源主图或分镜绑定。编辑预览调用它会提前替换原图。
- `imageService.upload` 不只是登记图片：带 `storyboard_id` 时立即绑定，并吞掉绑定异常。不能直接当作可靠的最终采用接口。
- `FilmCreate.doUploadResourceImage` 在已有主图时追加副图。直接调用它“编辑主图”会写到错误位置。
- 大图预览多处只保存 URL；URL 不能区分资源主图、副图、首帧、尾帧、历史图及素材库记录。

## 3. 图片身份与采用合同

### 3.1 打开窗口时必须固定的上下文

不是仅传 `url`，而是传以下概念数据；字段名属于本地实现设计，不是外部模型接口：

```text
source：实际选中图片的记录/字段、local_path 或 URL、图片身份
owner：drama/episode 上下文（从真实目标校验，不信任任意客户端值）
target：对象类型 + 对象 ID + 槽位（主图/副图/参考图/首帧/尾帧/历史/表单槽）
expected：原引用快照（含必要的图片 ID、路径和副图列表快照）
onAdopted：提交后更新原页面的选中项、表单或缓存
```

- 本地路径优先，URL 仅为读取来源；目标不能由 URL 反查后“全部替换”。
- 图片 ID 和业务对象 ID 分开保存；历史图可作为输入，但不是因此自动绑定到主图。
- `extra_images` 目前无条目 ID，采用时比较原列表/槽位值；发生并发变更就提示重新打开，不猜用户要改哪一项。
- 生成期间目标被删或图片引用变更：采用返回冲突，保留结果，不静默覆盖。
- 点击预览中的其他图片时同步更新完整上下文，不能只换显示 URL。

### 3.2 两个容易混淆的边界

**共享资源记录与共享文件不是一回事。** 如果多个分镜展示同一个角色记录，修改这条角色记录后其不同视图自然会显示新主图；不能声称这是分镜私有替换。入口须标明正在编辑哪个资源。其他独立记录只是引用同一旧文件时，不联动修改。本方案不为分镜偷偷克隆角色；若用户要求“同一角色仅这一镜换图”，那是另一个引用模型需求，应先确认，不能在本次暗加。

**表单草稿不等于已保存业务记录。** 尚未提交的参考图/自由创作参考槽沿用原输入生命周期；编辑采用是“最终文件保存并回填原输入”，不是替用户提交整个表单。界面必须区分“已应用到当前输入”和“已保存到资源”。未完成原有上传/添加的文件先完成该步骤，再允许编辑；不加第二套直接选图编辑入口。

具体接法：在已有参考图控件里复用 `uploadAPI.uploadImage` 上传所选文件，不提前绑定资源或提交表单；让参考图草稿同时保存预览与已上传路径。之后的 `save*RefImageIfAny` 优先复用当前草稿路径，不能又上传旧 data URL 把采用结果覆盖回去。参考槽展示主图占位时，源图可以是该主图，但采用目标仍须明确为参考槽，不暗改主图。

新增场景提交必须用 `const created = await sceneAPI.create(...)` 返回的 `created.id` 保存参考图；后端 `routes/scenes.js#create` 已直接返回该场景。删除 `useScenes.js#submitEditScene` 中按地点、时间重新 `.find()` 的定位方式，不新增查询接口。同地点/时间允许存在多条场景，名称不是身份。创建成功但参考图保存失败时，把 `created.id` 留在当前表单，保留草稿供重试；下次走更新/补存，不重复创建，也不误写旧场景。

### 4.2 选区与坐标

1. 后端读取原图并规范 EXIF 方向；前端显示的输入与实际提交模型的输入使用同一份规范化文件和尺寸。
2. 选区在原图坐标系存储，预览半透明红色只是显示层；画笔写选区，橡皮移除选区，重复涂抹不累计强度。
3. 指针经容器偏移、图片留白、平移和缩放的逆变换落到原图坐标；处理 CSS 尺寸与设备像素比，不把浏览器坐标直接当图像像素。
4. 画笔大小明确按图像/屏幕尺度之一转换，涂抹中用 pointer capture；取消指针、拖出画布、触屏操作均不能留下卡住的绘制状态。
5. 本地遮罩采用明确的二值选区表示；导出时消除显示抗锯齿造成的“透明度等于强度”歧义。外部黑白/alpha 编码仅在协议适配层转换。
6. “有选区”根据有效选中像素判定，不根据是否曾画过判定；全部擦除后请求不带遮罩。
7. 撤销保留本轮笔画/操作并重绘，避免每一步复制整张高分辨率 RGBA；不提供跨轮历史。
8. 若模型需要尺寸调整，由后端统一变换原图与遮罩；先校验原始尺寸对应，再同步处理。模型限制未明确前不随意缩放。

### 4.3 对比和连续编辑状态

```text
editing → generating → comparing
                 └──→ editing（失败/超时，保留输入）
comparing → editing（继续：结果变输入，清空本轮选区/描述）
comparing → editing（返回调整：恢复本轮输入，保留选区/描述）
comparing → adopting → closed（已提交且来源页面同步成功）
                    ├→ comparing（确认未提交，可重试）
                    └→ reconciling（提交结果未知，查询回执）
reconciling → comparing（确认未提交）/ sync_pending（已提交，等待页面同步）
sync_pending → closed（按同一回执同步成功，不重复采用）
```

- “来源原图 A”“本轮输入 B”“本轮结果 C”分开保存；项目引用在采用前始终不动。
- 同宽高比用同一显示坐标系，左原图/右结果、分割线居中、同步缩放平移；比较时隐藏选区。
- 不同宽高比显式提示并并排展示，各自保持比例，不裁剪/拉伸。保存仍用原始结果文件。
- 滑条支持键盘与可访问名称，按钮有文字/标签；不把重要操作只放 hover 区域。
- `generating/adopting` 共用禁重复提交和关闭门禁；按钮、Escape、点击遮罩、路由切换不能绕过。采用期间还要冻结来源槽的提交、清空、换图，并用槽位版本拒绝迟到上传回写。
- 采用 HTTP 超时不直接视为未提交；进入 `reconciling` 查询。查询使用有限等待，持续断网后退出忙碌锁并展示“保存状态未确认”，允许重查或关闭，但关闭不能发弃用/删文件请求；恢复联网后先查回执，不自动重发生成。
- 已提交但页面同步失败进入 `sync_pending`，提示“文件已保存，页面同步失败”，只重试同一回执的回填/刷新，不回到可改图或重复采用状态；需要关闭时保留已提交结果，不宣称撤销采用。只有来源引用同步成功才显示完整采用成功。
- 普通关闭有未采用内容时使用 PRD 的确认文案；取消确认保留现场。上述提交未知/已提交状态不能套用“放弃即删除结果”的路径。
- 页面刷新/关闭用 `beforeunload` 尽力提醒；操作系统强退无法保证拦截，靠后端遗留任务和临时清理兜底，不宣称模型任务已取消。

配置页还有两个必须在接入处消除的假成功：表单 `validate` 失败后仍继续提交；后端 `updateConfig` 不改 `service_type` 但界面允许改。最小做法是让校验失败真正中止，并禁止修改已有配置的服务类型，新增配置另选类型。

### 5.2 新的外部调用边界

新增 `backend-node/src/services/imageEditClient.js`，只负责一个明确的编辑调用合同：

```text
输入：实际选定配置/模型 + 干净原图 + 可选独立遮罩 + 修改要求 + 超时/中止信号
输出：已校验的完整结果图片（及必要元数据）
```

- 不调用 `imageClient.callImageApi` 冒充编辑；可以复用经核实的读取/HTTP细节，但不能继承其普通生图端点、风格提示词注入或参考图退化逻辑。
- 无选区严格不传遮罩；有选区且模型不支持时直接拒绝；仅支持遮罩的模型必须有选区。
- 能力依据真实适配器/模型合同，必要时在现有配置 `settings` 中记录模型能力；未知能力按未就绪处理，不能让用户勾个开关就声称支持。
- 配置与连接测试未接通时明确提示“编辑协议尚未对接”，不把纯文本探测或一次文生图成功叫作图片编辑测试成功。
- 真实 URL、路径、鉴权、图片传输、遮罩编码、同步/异步返回、模型时限仍待用户后端完成。本文不预填 `/images/edits` 或其他猜测协议。
- 测试使用注入的本地假调用；若以后获准做界面模拟演示，显著标注“模拟结果”。生产调用不以模拟结果兜底。

### 6.2 本地应用 API 草案

以下全部是浏览器与本项目 Node 后端之间的路径，**不是用户模型服务的路径**；统一挂在现有 `/api/v1` 下。

| 请求 | 作用 |
| --- | --- |
| `POST /image-edits` | 校验来源/目标并建立会话，取得统一方向的原图、尺寸与快照 |
| `GET /image-edits/:id` | 返回状态、revision、输入/结果身份、当前任务及采用回执；未提交时不暴露准备文件的持久路径 |
| `GET /image-edits/:id/files/:role` | 同源读取本会话当前输入/结果，不接受任意文件路径 |
| `POST /image-edits/:id/generate` | multipart：修改要求、配置/模型、request_id、expected_revision、input_id、可选 mask；返回 task_id 和新 revision；重放规则见 §6.3 |
| `POST /image-edits/:id/continue` | 携带 expected_revision/result_id；校验后把该结果设为新 input_id，递增 revision 并使旧生成请求重放失效；响应丢失先 GET，不盲目再次推进 |
| `POST /image-edits/:id/adopt` | 携带 result_id/expected_revision；数据库目标用 phase=commit；页面目标先 phase=prepare 取得 adoption_id，再 phase=commit 交付最终引用，见 §7.3 |
| `POST /image-edits/:id/finish` | 仅确认页面同步并幂等清理临时文件；不提交业务采用，不改变最终文件归属；仅 adopted 会话可完成 |
| `DELETE /image-edits/:id` | 放弃已确认未提交的会话；活动生成/采用中拒绝。adopted 返回既有回执，不回滚业务或删除最终文件 |

“返回调整”只恢复本轮前端输入，不重新生成；下次 generate 明确替换当前候选结果。会话关闭及清理必须考虑前端还在读取的图，不随意删除本轮输入。

### 6.3 任务隔离与失败处理

- `async_tasks.type = image_edit`，`resource_id = image-edit:<session UUID>`；不挂角色/分镜/剧集数字 ID，不被旧生成恢复逻辑误认。
- 编辑器用 `taskAPI.get` 轮询；不新增 `GEN_RESOURCE`，不让 `useGenerationTaskSync.js` 把它计为角色/场景生成。
- `generationTaskStore.js` 的恢复筛选应明确排除编辑任务，作为防误识别门禁；不重写整个旧任务系统。
- 同一会话只允许一个活动生成。幂等只覆盖最近一次、尚未被后续操作取代的生成请求，不承诺跨轮保存所有请求映射；具体判定顺序如下。
- 超时由后端结束任务，前端也有有限轮询等待；网络暂时断开要提示结果未知并查询原任务，不自动重新付费生成。
- 更新结果前检查活动任务 ID 与会话状态。已超时/放弃的旧响应不能覆盖新一轮；能中止 HTTP 则中止，但不等于取消供应商任务。
- 启动时先沿用 `failOrphanedAsyncTasksOnStartup`，再按 §7.4 恢复所有编辑会话，最后才清理过期文件；不能只处理 generating，不自动重发模型请求。

**生成请求的有限幂等合同：**

1. 前端每次有意重新生成分配新 `request_id`；网络重试必须复用原 ID、expected_revision、input_id 和相同参数，不能自行生成新 ID。
2. 后端先查本会话最近一次请求：若仍属当前输入且没有后续客户端变更，ID、原 revision 和参数摘要全相同，返回原任务及其真实状态，包括已失败/超时的任务，不再次调用模型。同 ID 但参数不同返回 409。
3. 其他请求必须满足 `expected_revision === 当前 revision`、`input_id === 当前输入` 且状态允许生成；否则返回 409，并让前端 GET 同步。一次已接受的客户端变更递增 revision；任务完成/失败、GET 和续期不消耗 revision。
4. 接受新生成时，在同一 SQLite 事务中检查状态/revision、创建任务、保存最近请求元数据、递增 revision 并进入 generating，事务提交后才调外部模型。继续编辑、准备/提交采用、放弃也校验 revision 并使旧生成重放失效。
5. 因此 R1 完成、继续编辑并接受 R2 后，迟到的 R1 必须被拒绝；即使是“返回调整”后仍使用同一输入图，新的生成 revision 也会拒绝旧请求。只保留最近映射，不另造长期请求历史。
6. 更新生成结果时仍同时校验活动任务 ID 与当前会话状态。新请求摘要包括配置/模型、要求、输入身份和遮罩内容摘要，不把鉴权信息放入摘要或日志。

### 6.4 文件、读取与清理

- 临时目录放在 storage 旁独立的 `image-edit-tmp/<session-id>/`，不混入 `/static`、公共素材目录或项目导出。文件名由后端生成。
- 原图只读，必要时复制/规范方向到会话目录；模型结果和遮罩也只存该会话目录。`sharp` 已在项目依赖清单中，可用于解码、尺寸/方向校验和协议需要的转换。
- 本地路径校验 resolved/real path 在允许根内，防 `../`、绝对路径和符号链接逃逸。上传遮罩校验实际解码、尺寸、像素量和字节数，不能只看扩展名。
- 远程来源优先使用已有本地文件；确需下载时限制协议、重定向、大小与超时，不能提供任意 URL 代理或读取本机任意文件。localhost 的合法静态引用转换为受控本地路径。
- 原图同源展示避免跨域 Canvas 污染；不会为了 CORS 另引入第三方图床。日志不记录 Key、完整 Base64 或带密钥的 URL。
- 临时源图、mask、各轮结果始终归编辑会话；已提交采用的最终文件归原业务/页面输入流程。归属转移发生在 §7 的采用事务提交时，而不是 finish、HTTP 响应到达或用户关闭窗口时。
- 准备文件路径先登记在会话，再写入独立文件；准备阶段只返回 adoption_id/图片元数据，持久引用不得交给原表单、视频请求或其他入口使用。GET 也不能泄露未提交的持久引用。前端预览继续用受控会话文件 URL。
- 用户放弃已确认未提交的会话时，删除本会话临时文件与未交付准备副本；已采用会话的 finish 只删临时文件。中途不删当前输入、对比、重试仍需的图。
- 异常退出采用惰性回收：启动和新建会话时，先执行 §7.4 恢复，再扫描最后活动超过 24 小时的会话。正常编辑用会话心跳续期；GET tasks 不等于会话续期。实际活动中的任务/采用操作不参与回收。
- 过期但未提交的 prepared 文件从未交付，允许随临时数据回收；存在 adopted 回执时，最终文件永不进入本功能的 TTL 删除集合，即使 finish 请求根本没有到达、业务库尚无引用或页面已经关闭。不能用“无数据库引用”推断页面不用这张图。
- adopted 回执在会话最后活动后至少保留 24 小时，供响应丢失时查询/幂等重试；到期可以清理回执和会话临时文件，但不得删除或重新采用最终文件。已清理的会话请求返回不存在/过期，不自动创建新会话重试。
- 清理失败记录可重试状态，不把业务采用倒退成失败，更不能遍历删除旧素材。不存在“pending 文件已被原表单引用，再靠 TTL 猜是否能删”的合法状态。

## 7. 最终采用：复用哪些逻辑、怎样避免假成功

### 7.1 数据库目标

流程必须是：

1. 解码确认最终结果有效，核对会话及所选结果身份。
2. 从真实目标确定工程目录，复用 `storageLayout`；先登记 adoption_id、result_id 与准备路径，再写独立文件并校验完整性，不覆盖原文件。采用过程对本会话互斥，不能与生成、继续、放弃或另一采用并发执行。
3. SQLite 事务中重读目标、比较原引用快照、更新业务记录/必要的最终历史，同时写 adopted 状态及采用回执；回执包含 adoption_id、result_id、最终引用和必要的新图片 ID。
4. 事务成功后最终文件脱离会话回收，才向前端返回引用；前端同步实际采用记录及选中状态，不只替换图片 URL。
5. 原页面完成同步后清理临时文件。若刷新失败但数据库已经提交，明确“已保存，显示刷新失败”，按回执重新加载，不能谎称保存没发生。

文件系统与 SQLite 无法组成同一个原子事务：最终文件先准备，事务失败则原引用不变、结果仍可重试；会话记录待采用路径以便回收无引用的孤立副本。不能先删临时图，也不能先绑一个尚未落盘的文件。

重复点击或响应丢失时，先匹配同一会话/result_id/adoption_id 的已有回执，再处理 revision 检查，避免成功请求的原 revision 被误判为新的冲突；已提交会话拒绝另一结果的采用，不再插入第二份历史。只在确定事务未提交时回收准备的最终文件；状态不明先查询，不能误删已经被引用的图。

### 7.2 原保存服务的必要小改动

| 文件 | 计划改动 |
| --- | --- |

首/普通图更新 `image_url/local_path/first_frame_image_id`；尾图更新 `last_frame_image_url/last_frame_local_path/last_frame_image_id`。编辑历史图只登记新记录，不执行帧绑定；旧记录及它在别处的引用保留。

特别处理旧数据没有显式绑定的情况：仅把读取顺序改为“绑定优先”还不够，最新历史仍可能被 fallback 自动选中。未绑定编辑结果使用明确的 `frame_type = image_edit_history` 标记（现有 TEXT 字段），保留在历史列表，但排除在“自动选最新主图/按类型回退”的候选之外；用户以后主动选择它时仍可按图片 ID 绑定。列表与画布同时处理，测试覆盖无绑定旧数据，不新增默认绑定来假装“引用没变”。

**绑定图片与 100 张分页的合同：**

1. 历史列表仍按原分页加载，不为了找绑定图拉全量历史。明确绑定 ID 存在时，它的优先级高于当前页、旧选择缓存、同类型图片和最新图片。
2. 绑定图不在当前页，但该槽有权威 URL/local_path：直接构造带该绑定 ID 的显示记录；不得先返回当前页另一张同类型图片。首/普通图只读主图字段，尾帧只读 last_* 字段。
3. 绑定 ID 存在而槽位路径缺失：通过已有 `GET /images/:id` 补取该记录，并检查其分镜归属。补取缓存与历史分页分开；失败明确显示该绑定图不可用，不静默换图。前端 `imagesAPI.get(id)` 同时供此处和自由创作使用。
4. 只有不存在显式绑定 ID/槽位引用时，才使用旧图的同类型/最新回退，并排除 image_edit_history。`composed_image` 等已明确来源也不能被新历史抢占。已手工选中的 image_edit_history 按明确绑定正常展示。
5. 无绑定老数据也不能先截断 100 张再排除编辑历史：当前页无合法回退图时，通过现有 GET /images 补查一条候选，数据库查询先排除 image_edit_history/quad_grid/nine_grid 再分页；首尾帧附带原有 frame_type 条件。新增 exclude_frame_types 查询参数，不新增接口、不修改普通历史列表结果。否则连续追加 100 张编辑历史仍会把旧显示图挤没。
6. `FilmCreate` 与 `storyboardMedia.js` 使用同一解析规则；`useCanvasStoryboardMedia.js` 和列表加载处负责按需补取，不在纯解析函数中发请求。采用/刷新后同步权威绑定，旧缓存不能盖过新绑定。

### 7.3 纯页面/未提交表单目标

不能宣称 SQLite 事务能覆盖 Vue 内存。采用明确的“准备 → 提交交付 → 回填 → 清临时文件”顺序，**不允许先把 pending 持久路径写进原页面，再等 finish 决定其存活**：

1. 前端固定来源页面实例/槽位版本，确认原值未变并冻结该槽；后端收到 adopt(phase=prepare) 后准备文件，进入 prepared，只返回 adoption_id、result_id、新 revision 与尺寸等元数据，不返回可供旧接口保存的持久引用。此时无新图片历史，无外部引用。
2. 前端预先构造本地更新所需数据、验证目标仍存在；这一步不改变实际参考槽、结果项或表单，也不发原业务保存请求。准备失败可以回到对比/放弃，旧引用不变。
3. 前端收到准备结果后发 adopt(phase=commit)，携带同一 adoption_id/result_id/expected_revision。后端校验准备文件，在事务中写 adopted 回执并转移最终文件归属。自由创作的最终独立 `image_generations` 记录也只在这一事务中创建；普通参考槽不新增图片历史，不替用户提交资源表单。
4. 提交成功响应或 GET 回执才给出最终引用。前端按已验证的槽位版本同步回填预览、路径、必要图片 ID；页面目标的回填是小的同步状态替换，不夹带再次上传/生成/异步业务保存。成功后提示“已应用到当前输入”，调用 finish 清理临时文件并关闭编辑器。
5. 提交前任何失败都保持旧槽位，可重试同一准备结果。提交状态未知只查询；已提交后如页面意外失效或回填失败，保留旧页面引用并进入 sync_pending，重试回填使用同一回执，不再次登记历史。不能把这种情况伪报为“后端未采用”，也不能删除已交付文件。
6. finish 只是清理确认。请求未发送、请求未到服务器、响应丢失均不影响最终文件；重复 finish 无副作用。已 adopted 的自由创作记录也不会因 finish 失败被回滚。

页面输入原本不跨刷新恢复，本功能不新增结果列表恢复功能。已提交后发生进程退出，只能保证最终文件/记录不丢、未提交文件不被引用，不能保证 Vue 内存与 SQLite 跨进程原子提交；这与数据库采用后响应丢失一样，必须以回执区分“未保存”和“已保存但页面未同步”。“只保留最终结果”仍然排除所有生成中间图；提交阶段最多持久登记本次明确选择的一张最终图，不把每轮候选登记到历史。

### 7.4 采用超时、重启与恢复

`adopting` 是短暂操作状态，不能作为永久锁。后端用会话级活动操作标记避免并发；恢复只能在该操作已结束，或新进程启动确认旧操作已不存在时执行，不能让客户端网络超时直接清理仍在工作的服务端文件。

| 重启/重查时的证据 | 必须恢复到的结果 |
| --- | --- |
| 有已提交采用回执 | 恢复 adopted，返回同一最终引用/记录；不再复制文件、写历史或执行业务更新，绝不因缺 finish 回收最终文件 |
| 无回执，停在 adopting，准备文件尚未完整 | 确认旧操作不存在后，移除本会话残缺准备副本，保留生成候选，恢复 comparing，允许重试/关闭 |
| 无回执，数据库目标的准备文件完整，但业务事务未提交 | 恢复 comparing，保留候选及可复用准备副本；重试重新检查目标快照，不自动提交旧采用 |
| 无回执，页面目标的准备文件完整 | 恢复 prepared，保留同一 adoption_id；客户端重新核对页面槽后可提交，也可放弃/过期回收，因为持久路径尚未交付 |
| 已有 prepared，无活动操作 | 不保持 adopting 锁；按 prepared 的提交/放弃/续期规则处理 |
| 回执存在但最终文件因磁盘故障/外部删除缺失 | 明确报已提交文件不可用，保留证据；不退回未提交状态、不用旧图冒充成功、不重复登记 |

启动顺序固定为：数据库完成迁移/事务恢复 → 旧 async_tasks 标失败 → 核对编辑会话及采用回执 → 解除失效操作状态 → 清理满足条件的过期会话。所有业务写入与采用回执必须同事务，因此在数据库正常恢复后，无回执意味着该采用事务未提交；检查数据库失败则保留状态与文件，不猜测未提交。

采用操作有有限服务端期限：在可中止的文件准备步骤检查期限，失败走统一 finally 释放活动标记并写可重试状态；同步 SQLite 事务以实际提交结果为准，不能在已提交后改写成失败。前端超时进入 §4.3 的查询状态，重启或重查都不能自动再次调用模型。
